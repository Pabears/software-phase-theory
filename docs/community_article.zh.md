# 什么软件需要 LLM？先定物态，再动代码
## ——软件物态学的一份实操分诊清单

> 本文是 `ask-shiheng` 编码前架构分诊 Skill 的配套文章。仓库：[Pabears/software-phase-theory](https://github.com/Pabears/software-phase-theory)（CC BY-SA 4.0）。转载请注明作者与出处。

**两个真实的反面场景，先对号入座：**

场景 A：团队把"核心账本平账与状态流转"交给了一群互相讨论的 Agent。Demo 很惊艳，上线第三周开始出现幻觉坏账——因为账本逻辑本质是 `[目的定死, 过程定死, 结果定死]` 的纯确定性问题，却硬塞给了概率模型。

场景 B：团队把开放式发票文本解析写死成一万行正则。上线第二天，供应商换了个排版，解析器当场雪崩——因为开放文本解析本质是 `[目的定死, 过程柔性, 结果锁死]` 的偶发复杂度问题，却用死代码去硬刚真实世界的微扰。

**大多数 AI 工程灾难，不是模型不够强，而是物态放错了。** 这就是"软件物态学"要解决的第一性问题：什么软件需要 LLM？

## 一、三维坐标：`[目的, 过程, 结果]`

把任何一个功能模块放进由三个自由度张成的因果相空间：

- **目的（Telos）**：这个模块要达成什么，是否已经被彻底想清楚？
- **过程（Process）**：达成路径是否完全确定，还是需要现场探索？
- **结果（Schema）**：输出结构是否强类型锁定？

每个维度取值 `1`（确定锁死）或 `0`（柔性开放），组合出软件的几种形态：

| 坐标 | 形态 | 铁律 | 最经典错配 |
| :---: | :--- | :--- | :--- |
| `[1,1,1]` | 🪨 固态 | 纯确定性代码，**严禁引入概率 LLM** | 账本液化幻觉态 |
| `[1,0,1]` | 💧 液晶态 | LLM + 强 Schema 掩码，单步提取 | 过冷正则脆断态 |
| `[1,0,0]` | 🌊 受控液态 | 百行极简探针 + 四重防爆沙盒 | 容器破裂裸奔态 |
| `[0,0,0]` | ☁️ 无界气态 | 开放采样，与生产写操作物理隔离 | 回音室扯淡耗散态 |
| `[0,1,1]` | ⚠️ 僵尸态 | **目的未定却锁流程/格式——当场叫停编码** | 形式主义空转态 |
| `[0/液]→[1,1,1]` | 💎 制度性晶体 | Object + Link + Kinetic Action 2PC，提议与提交物理分离 | 伪气态套壳泡沫 |

三句话记住四种实用形态：

1. **算账、权限、CRUD、编译器——固态**。写死状态机与 ACID，谁提议把 LLM 放进核心账本，谁就是在制造幻觉坏账。
2. **非结构化转 JSON/AST、分类提取——液晶态**。这是 LLM 的主战场：目的明确、输出 Schema 锁定，只差一步"偶发复杂度消除"。铁律是**单步提取，劝退多轮 Agent**——多轮链条每多一环，级联误差就多乘一次。
3. **未知异常排障、动态脚本合成——受控液态**。Agent 的正当用武之地，但**液体不能承重**：只读沙盒、命令白名单、轮次熔断，四重防爆缺一不可。
4. **脑暴、草拟、陪伴——无界气态**。开放采样随便飞，但必须与生产写操作物理隔离。

## 二、三问把脉：从"想做什么"到"怎么验收"

框架之外，还需要三把尺：

**第一问：定物态。** 逐模块标坐标，对号入座排查错配（上面的表）。

**第二问：定裁判。** AI 参与的模块，谁来验收？三档选配：
- 🛡️ **A 档：符号固态门禁**——编译器、AST、Schema、单测、Z3/ASP 求解器自动把关，失败即回滚。写代码、SQL、API 必选。
- 👀 **B 档：双模型初筛 + 人在环终审**——Critic LLM 查漏，落盘前必须人类拍板。写文档、方案选这个。
- 🎲 **C 档：纯 LLM 自省放飞**——高容错实验可以选，但请知情：PlanBench 实测纯大模型自验的假阳性率约 **84.45%**（Valmeekam et al., arXiv:2310.08118），可能把对的改错。风险透明，选择权在你。

**第三问：定数据线。** 拒绝一上来就画"全量知识图谱"或"万能多 Agent 平台"。只问一句：**本期唯一真实写操作（Kinetic Action）是什么？** 围绕这一个 Action 逆向倒推最小实体、关联与回滚边界。AI 永远只产**提议**，固态代码执行**提交**——提议与提交物理分离，是 AI 系统接入现实世界不翻车的底线。

## 三、一句话总纲

> **固态守其常，液晶取其巧，液态控其界，晶体收其功。**
> 先定物态，再动代码；无处方，不动刀。

## 四、怎么用起来

这套方法论有一个可执行版——`ask-shiheng` Skill。它在任何 AI 编码工具（DeepSeek Harness / Claude Code / Gemini CLI 等）写第一行代码**之前**被强制唤起，走完三问把脉，输出一页纸《物态架构处方单》，固化为项目根目录的 `PHASE_SPEC.md`，成为后续所有编码 Agent 的最高宪法。

```bash
git clone https://github.com/Pabears/software-phase-theory.git
cd software-phase-theory
ln -s "$PWD/skills/ask-shiheng" ~/.dsh/skills/ask-shiheng   # DSH
# 或 ~/.claude/skills/ask-shiheng（Claude Code）/ ~/.gemini/config/skills/ask-shiheng（Gemini CLI）
```

仓库里还有完整的理论手册、四篇命题核查报告、45 篇文献索引（arXiv/DOI 直链，零 PDF 入库）、以及一份[发票智能入账服务的示例处方单](https://github.com/Pabears/software-phase-theory/blob/master/examples/PHASE_SPEC.example.md)。

## 五、写在最后

这不是一篇"AI 万能"或"AI 无用"的站队文。软件物态学的全部主张可以浓缩成一句谦逊的话：**让确定的归代码，让柔性的归模型，让探索的归沙盒，让写回的归晶体。** 边界放对了，两者都省心。
